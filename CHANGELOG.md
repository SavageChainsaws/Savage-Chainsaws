# Changelog

Owned by Stem. One line per change: date, who, what, and why if it's not obvious. Everyone on the team — Claude, Stem, App Bot, New Bot, Financial Bot — checks this file and `docs/HANDOFF.md` before building anything new, and adds a line here for every change they make. Newest entries on top.

Only Claude writes code or runs migrations (see `docs/HANDOFF.md` §7) — an entry here from a bot describes data it entered or an action it took through an existing API route, never a code or schema change.

## 2026-11-09

- **[Claude]** Fixed three issues Stem found reviewing the Unit Bot PR, pushed to the same branch (still not merged): **(1) blocker)** `lib/bot/respond.ts` was logging every failed/unauthenticated call under `botName: requiredBot` - the bot the caller was *trying* to reach, not an identity it had actually proven - and `checkRateLimit` counts every `bot_audit_log` row for a `bot_name` regardless of outcome, so a flood of bad-token requests alone could fill a real bot's own rate-limit window and lock out its valid token. Fixed by logging those under a new `ANONYMOUS_BOT_LABEL` (`'anonymous'`, in `lib/bot/audit.ts`) instead, which no real bot's rate-limit query ever matches; `logBotAction`'s `botName` param loosened from `BotName` to `string` to allow it. New `lib/bot/respond.test.ts`: 150 bad-token requests in a row don't rate-limit a subsequent valid App Bot token, and a bot's own 120 real logged calls still correctly trip `429`. **(2)** `UNIT_BOT_PATCH_FIELDS` allowed `part_number` (singular) - a real column, but confirmed by grep to be a dead one nothing else in the app reads or writes (only `part_numbers`, plural, is wired into the real fleet forms) - removed it from the allowlist so Unit Bot can no longer write to a field nothing else ever looks at. **(3)** The service-history create route's audit entry only recorded the unit's *new* `hour_meter`/`last_service_date` when it bumped them, never what they were before - added a `before` object built from the unit row already fetched for the update, so the audit log now shows both sides of the change like every other Unit Bot write does.
- **[Claude]** Opened a PR adding a third bot scope, Unit Bot (`/api/bot/unit/*`), same pattern as App Bot/Financial Bot: a hashed bearer token in `bot_tokens` (widened `bot_tokens_bot_name_check` to admit `'unit_bot'`), minted at `/bot-tokens`, every call written to `bot_audit_log` (now including before/after values for every update), `Idempotency-Key` required on every write, and a new shared rate limiter (`lib/bot/rateLimit.ts`, 120 calls/60s per bot scope) applied to all three bots, not just the new one. Unit Bot can read/create/update units (`model`/`serial_number`/`equipment_type`/`hour_meter`/`part_number(s)`/`nickname`/`fleet_notes`/`notes`/`purchase_date`/`last_service_date`/`customer_id`-to-an-existing-customer-only - `archived` is deliberately **not** in that list, see below), add/edit its own service-history entries (new `service_history.created_by_bot_name` column gates edits to entries it created itself), read/upsert `model_parts`/`unit_part_overrides`, read parts-catalog/spec-sheet reference data, add unit photos, and update per-unit customer notes. Hard limits (no `DELETE` anywhere - guarded by a dedicated regression test; no `invoices`/payments/`bot_tokens`/auth tables; no customer contact info beyond id+name; no customer-facing emails; can't touch `parts_catalog`/`rotary_parts` pricing) are enforced in route code, not just described. **Flagging explicitly rather than silently substituting**: the request's alt-vendor parts cross-reference (`rotary_sku`/`rotary_oem_ref`/`alt_vendor`/`alt_part_number`/`alt_notes`) named `service_parts_list`, one of the four already-flagged abandoned-prototype tables (RLS disabled, keyed off an unrelated integer `equipment_id`, no path to a real `units.id`) - added those five columns to `unit_part_overrides` instead, which is real, `unit_id`-linked, and RLS-enabled. Also flagging: Unit Bot's scope (units, service history, parts, photos, notes) looks like it may be "New Bot" (from the original team roster) getting its own token under this access model, not a genuinely new fourth bot - unconfirmed, needs Stem/Jesse to say which. **PR opened, not merged - Stem reviews first, same as the original bot-access PR.** No new `service_role` GRANTs needed - the 2026-11-09 hotfix below already covers every table this touches.
- **[Claude]** Production incident, found and fixed live: both App Bot and Financial Bot got `401 Not authorized` on every call right after tokens were generated, with zero entries in `bot_audit_log`. Root cause, confirmed via Supabase's own API logs: `service_role` has `BYPASSRLS` (RLS was never the gate) but had **no table-level `GRANT`s at all** on `bot_tokens`/`bot_audit_log`/`bot_idempotency_keys`, and only partial grants on `invoices`/`units`/`service_history` - the original migration granted `authenticated`, never `service_role`. RLS bypass and Postgres's `GRANT` system are two separate layers; only the first had been addressed. This also explained the missing audit entries: the audit INSERT itself was being rejected by the same gap, not silently skipped. Applied `20261109060000_grant_service_role_access.sql` directly to the live database (pure additive `GRANT`s, no data/behavior risk) - `service_role` now has full access on every table/sequence/routine in `public`, plus `ALTER DEFAULT PRIVILEGES` so a future new table can't silently repeat this. **Fixed immediately at the database level - no app redeploy was needed.** This same gap had likely already been silently affecting every pre-existing `createAdminClient()` caller in this app (Stripe/Square webhooks, customer-login creation, Zelle claims) - not something this PR introduced, just never exercised hard enough to surface before now.

- **[Claude]** Fixed a second round of real bugs from Stem's re-review (at commit `db2d6da`): `sendInvoiceEmail` now flips `status` to `'sent'` too (not just `sent_at`), since a bot-created draft that gets emailed was otherwise staying `status='draft'` forever and silently dropping out of the Financial Bot summary's "outstanding" aggregate, which filtered on `status != 'draft'`; that query also now falls back to `sent_at IS NOT NULL` as a second signal, so the two can never drift apart again. Square's paid-amount check now fails closed on an *unknown* amount (`paidAmountCents === null`, which happens when `order.state === 'COMPLETED'` but there are zero tenders), not just a mismatched one - previously an unknown amount skipped the check entirely and could mark an invoice paid with nothing actually verified. The units duplicate-safeguard index now also excludes the empty string (`serial_number` is NOT NULL, so "no serial yet" is always `''`, never `null`) - without it, a second serial-less unit for the same customer 500'd instead of being allowed, same as a second "Unknown" one already correctly is. The draft-invoice PATCH route now preserves an existing referral discount when line items are edited (it was silently dropping it, overcharging the customer) and rejects a negative total, matching create's own billing math; it also re-checks `sent_at` before overwriting the PDF a second time (after the storage upload), not just before the line-items update. Idempotency claims now expire after 60s of being stuck unresolved (a crashed request no longer locks that exact key out forever), and a real insert failure (not the idempotency-key conflict itself) is reported as an error instead of being mistaken for "already in progress." Confirmed `UNIQUE(lower(email))` on `customers` is genuinely live (via `pg_indexes`, not just asserted) and corrected `docs/HANDOFF.md`'s unit-index line to mention the `trim()`. Bot-created units now default to `status: 'Fleet'` (not `'Received'`, which isn't what either admin creation flow actually uses and would wrongly show up as "in for service"). The reminder email now HTML-escapes every interpolated value. Re-verified the live-data duplicate check against the final index expression - still clean. **Still not applied/deployed.**
- **[Claude]** Fixed real correctness/safety bugs Stem caught in its read-only review of the bot-access PR before any merge: reminders now gate on `sent_at` (not `status`, which is set at PDF-creation time before any email ever goes out); bot-created invoice drafts now apply the same first-service referral discount the admin flows do and reject a negative total; `units.serial_number` (NOT NULL) is never sent `null` from the bot route; the duplicate-unit index now trims before lowercasing, consistent with its own `WHERE` clause; every bot read (not just writes) is now audited; `GET /api/bot/app/customers?id=` no longer `select('*')`s; added a test for a revoked token. Re-verified the live-data duplicate check against the corrected index expression - still clean. **Still not applied/deployed - same approval gate as below.**
